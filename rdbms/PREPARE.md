# RDBMS 다음 작업: prepare/describe와 실행 요청 취소

## 현재 상태

- 작성일: 2026-10-20.
- 상태: **구현 반영·최종 검증 미완료**. 아래 요청의 서버 코드와 확장 규약을 반영했다. 사용자 지시에 따라 마지막 오류 수정까지만 진행하고 추가 테스트를 다음 작업으로 넘겼다. 최신 구현 상태·실패 기록·재개 절차는 [HANDOFF.md](HANDOFF.md)를 먼저 읽는다. 아래 체크박스는 검증까지 포함한 완료 기준으로 남겨 두며, 모두 미구현이라는 뜻은 아니다.
- 배경: 사용자가 Windows ODBC 계획을 작성하면서 서버 쪽 prepare/describe·cancel 구현도 다음 작업에 명시하도록 요청했다.
- 현재 구현과 시험 결과는 [PROGRESS.md](PROGRESS.md), 현재 통신 규약은 [docs/protocol.md](docs/protocol.md)가 기준이다. 구현 전에 [AGENTS.md](../AGENTS.md)의 관련 상세 사양과 통신 문서를 먼저 갱신한다.
- 이 파일이 새로 만들어졌으므로 기존 PROGRESS.md를 대체하지 않는다. 작업 완료 시 두 문서의 상태를 함께 갱신한다.
- 다음 작업 순서: **PD-1 ~ PD-5 구현 검토·집중 시험 → PD-6 전체/호환 회귀 → 문서 갱신·완료 판정**. JDBC 마지막 수정 뒤 재빌드·재시험과 최종 Node.js 22 전체·Bun 시험이 남아 있다.

## 필요한 이유와 완료 목표

1. `SQLPrepare` 뒤 `SQLDescribeCol`·`SQLNumResultCols`를 호출하는 ODBC 앱에 실제 실행 전의 결과 메타데이터를 제공해야 한다. SELECT를 실제로 실행하거나 DML을 실행했다가 롤백하는 방식으로 메타데이터를 알아내지 않는다.
2. 서버에서 알 수 없는 파라미터 타입은 unknown으로 구분한다. 값이 아직 없다는 이유로 임의의 VARCHAR나 DECIMAL(10,3)을 확정 타입으로 보내지 않는다. ODBC의 선택 기능인 SQLDescribeParam과 필수 결과 메타데이터를 구분한다.
3. `SQLCancel`·질의 제한 시간을 접속 종료에만 의존하지 않고 구현하려면, 실행 중인 요청을 별도 요청으로 취소할 수 있어야 한다. ODBC 쪽 의존 단계는 [winodbc/PROGRESS.md](../winodbc/PROGRESS.md)의 WO-6·WO-8·WO-13이다.
4. 기존 드라이버의 hello/auth/execute/fetch/close 동작은 유지한다. 새 요청을 모르는 구형 서버와 신형 드라이버의 조합도 기능 협상으로 판별한다.

## PD-1. 사양과 기능 협상부터 확정

- [ ] AGENTS.md 상세 8과 프로토콜 문서에 기능 범위·권한·수명·오류·동시 요청 예외를 추가한다. 저장 프로시저, SQL 텍스트의 PREPARE 문법, 실행 계획 영구 저장은 이번 범위에 넣지 않는다.
- [ ] helloOk의 선택적 기능 목록 등으로 새 기능을 알리는 방식을 정한다. 아래 메시지 이름은 **설계 제안**이며 구현 전 protocol.md에 확정한다.
- [ ] 준비 문장 ID와 커서 ID의 이름공간·한도·해제 규칙을 분리한다. 현재 커서 16개 제한을 준비 문장 제한으로 재사용하지 않는다. 준비 문장 한도는 별도 정하고 시험한다.
- [ ] 요청을 차례대로 처리하는 기존 규칙에 cancel만 예외를 허용한다. cancel 응답과 원래 execute 응답을 각각의 id로 연결하는 규칙을 정한다.
- [ ] 구형 서버·신형 서버, 구형·신형 클라이언트의 조합 표를 만든다. 새 요청 추가가 기존 규약과 호환되는지 검토하고 필요한 프로토콜 버전·기능 협상 정책을 문서에 확정한다.

구현에 반영한 메시지 역할(확정 필드는 protocol.md 17절 참고):

| 요청 | 응답 역할 | 주의점 |
|---|---|---|
| `prepare {sql, parameterTypes?}` | 준비 문장 ID, 파라미터 개수, 결과 종류·컬럼 정보 | 값을 실행하지 않는다. parameterTypes는 타입 힌트이며 데이터 값이 아니다 |
| `describe {statement, parameterTypes?}` | 준비 문장의 결과·파라미터 메타데이터 | 결과 없음·타입 미정·오류를 서로 구분한다 |
| `executePrepared {statement, params, fetchSize?}` | 기존 rows/ok/error와 같은 결과 전달 | 실행 시 권한·객체 유효성을 다시 검사한다 |
| `closePrepared {statement}` | 해제 확인 | 이미 해제한 ID의 처리 규칙을 명시한다 |
| `cancel {targetId}` | 취소 접수 여부·이미 종료·취소 불가 단계의 구분 | cancel 자체에도 새 요청 id가 필요하다 |

완료 기준: 요청/응답 예시, 상태표, 오류 목록과 하위 호환 시험 목록을 코드보다 먼저 작성한다. 원래 execute의 최종 응답과 cancel 접수 응답을 같은 응답으로 취급하지 않는다.

## PD-2. 실행하지 않는 분석·결과 메타데이터

- [ ] SQL 파싱·바인딩·타입 분석을 실행기에서 분리하거나 재사용하여 분석 전용 API를 만든다. 객체·뷰·컬럼·파라미터 위치를 분석한다.
- [ ] SELECT의 별칭·별표·조인·집계·CASE·CAST·집합 연산·서브쿼리·뷰 확장을 데이터 행을 읽지 않고 분석한다. 길이·precision·scale·소수 초·INTERVAL 한정자는 실제 타입 정의를 따른다.
- [ ] 파라미터 타입을 컬럼 문맥·CAST·명시적 타입 힌트로 알 수 있는 경우와 알 수 없는 경우를 구분한다. `SELECT ?`처럼 결과 타입도 미정이면 이를 명시하고, 타입 힌트를 받아 다시 분석할 수 있게 한다.
- [ ] INSERT/UPDATE/DELETE/DDL의 분석도 데이터를 변경하거나 DDL의 자동 커밋을 일으키지 않는다. DEFAULT·CURRENT_TIMESTAMP 등의 표현식을 값으로 평가하지 않는다.
- [ ] 현재 테이블스페이스가 null인 사용자, 큰따옴표 식별자와 특수 이름을 처리한다. 이름 해석과 권한 검사는 기존 규칙을 재사용한다.
- [ ] 뷰 권한으로 접근할 수 있는 컬럼은 분석할 수 있어야 하지만 기반 테이블에 대한 별도 권한을 우회하여 추가 정보를 노출하지 않는다.

필수 시험: 분석 전후 테이블 데이터·객체 목록·세션 현재 테이블스페이스·자동 커밋·진행 중 트랜잭션·잠금·저장 파일이 달라지지 않아야 한다. 실행되지 않은 INSERT·UPDATE·DDL을 시험에 반드시 포함한다.

완료 기준: 최소 `SELECT 1`, `SELECT * FROM T`, `SELECT CAST(? AS DECIMAL(12,0))`, 조인·뷰 질의의 메타데이터를 실제 실행 없이 얻는다. 결과 타입 미정은 정확히 미정으로 보고한다.

## PD-3. 준비 문장 저장·무효화·실행 연결

- [ ] 세션별 준비 문장 레지스트리를 만든다. SQL/AST·메타데이터·분석 당시 이름 해석 정보·객체 의존성을 보관하고 다른 세션에서 ID를 쓰지 못하게 한다.
- [ ] 테이블스페이스 변경, 객체 DROP/ALTER, 뷰 교체, 권한 GRANT/REVOKE 뒤의 동작을 정한다. 같은 이름으로 재생성한 다른 객체를 기존 객체로 오인하지 않는다.
- [ ] executePrepared는 기존 문장 실행·권한·트랜잭션·커서 경로를 재사용한다. 준비 시 허용되었다는 이유로 실행 시 권한 검사를 생략하지 않는다.
- [ ] 명시적 해제·연결 종료·인증 실패·서버 종료에서 리소스를 정리한다. 준비 문장 해제와 이미 반환한 결과 커서 해제의 관계를 명세대로 처리한다.
- [ ] 한도 초과·잘못된 ID·해제 후 실행·교차 세션 ID·객체 변경 후 실행을 각각 시험한다.

완료 기준: 같은 문장을 반복 실행할 수 있고, 권한 회수는 다음 실행부터 반영된다. 누수 없이 한도까지 할당·해제를 반복한다.

## PD-4. 취소 가능한 실행 컨텍스트

- [ ] 세션 전체가 아닌 **실행 요청별** 취소 토큰·요청 ID·실행 단계를 둔다. 이전 요청의 늦은 취소가 다음 요청에 적용되지 않게 한다.
- [ ] 잠금 대기는 기존 cancelWait와 연결하되 세션을 닫지 않는다. 문장 단위 복구 경로를 재사용하여 해당 문장의 변경만 되돌린다. 기존 트랜잭션의 앞선 성공 문장은 보존한다.
- [ ] 스캔·조인·집계·정렬·DML 대상 순회·제약 검사 등 긴 구간에서 취소를 확인한다. 확인만 하지 말고 일정 작업량마다 이벤트 루프에 제어를 돌려 cancel 패킷이 실제로 처리되게 한다.
- [ ] 큰 Array.sort 등 한 번의 동기 호출이 장시간 막는 구간도 확인한다. 단계별 정렬/병합 등 중단 지점을 갖는 방법을 설계하고 Node.js·Bun에서 검증한다.
- [ ] 자동 커밋 DML의 변경 확정 경계를 명시한다. 변경이 확정된 뒤에는 취소 성공을 돌려주거나 이미 커밋한 내용을 롤백했다고 알리지 않는다.
- [ ] DDL·GRANT/REVOKE·COMMIT처럼 되돌릴 수 없는 단계의 취소 정책을 별도로 정한다. 초기에는 변경 확정 이후 tooLate를 반환하는 정책을 기준안으로 삼는다. DDL 전의 자동 커밋까지 되돌린다고 약속하지 않는다.
- [ ] 취소된 SELECT의 임시 결과·커서, 취소된 DML의 오버레이와 잠금 대기 리소스를 정리한다. 잠금 유지/해제는 기존 문장 실패·트랜잭션 정책과 맞춘다.

필수 시험: 긴 CPU 질의 도중 다른 연결의 ping과 cancel이 실행 완료 전 처리되어야 한다. 잠금 대기 취소만 성공한 상태로 전체 취소 구현을 완료 처리하지 않는다.

## PD-5. 취소 요청의 우선 처리와 결과 경합

- [ ] READY 상태의 같은 인증 연결에서 자신의 실행 요청만 취소하도록 한다. 임의의 세션 ID를 받아 다른 사용자의 작업을 취소하는 관리 기능은 추가하지 않는다.
- [ ] cancel은 실행 대기열 끝에서 기다리지 않도록 수신·검증 후 별도 경로로 처리한다. 단, 일반 execute 두 개를 동시에 실행하도록 직렬화 규칙을 풀지 않는다.
- [ ] 원래 요청에는 정상 결과 또는 취소 오류 중 하나만 보낸다. 취소 오류 SQLSTATE는 `57014`를 기준안으로 검토하고 내부 번호는 기존 번호를 바꾸지 않고 새로 배정한다.
- [ ] cancelAck의 accepted는 접수 사실일 뿐, 실행 취소 완료를 보장하지 않는다고 규정한다. 완료 직전·완료 직후·중복 cancel·알 수 없는 targetId를 시험한다.
- [ ] TCP·TLS·로컬 채널·UDP 모두 같은 의미를 제공한다. UDP 중복/재전송에서도 하나의 실행이 두 번 취소되거나 두 번 실행되지 않아야 한다.
- [ ] 클라이언트는 단일 수신 경로에서 id별 대기 요청을 나눈다. execute가 응답을 기다리는 동안 cancel을 보낼 수 있어야 한다. 두 스레드가 같은 소켓에서 각자 read하여 응답을 빼앗지 않게 한다.
- [ ] 서버 종료·연결 끊김·시간 초과·정상 완료와 취소의 경합을 시험하고, 통신 단절로 결과를 모를 때 자동으로 DML을 다시 실행하지 않는다.

완료 기준: 취소 후 연결을 재사용하고 같은 수동 트랜잭션의 앞선 변경을 커밋할 수 있다. 취소할 수 없는 단계에서는 사실대로 tooLate/정상 결과를 보낸다.

## PD-6. 회귀·드라이버·ODBC 완료 기준

- [ ] 분석/준비/실행/해제 단위 시험과 모든 접속 경로의 실제 서버 시험을 추가한다.
- [ ] 기존 rdbms 시험과 Node.js·Python·jdbc6·jdbc8의 실제 서버 회귀 시험을 실행한다. 지원 범위를 벗어난 런타임에서 통과한 결과를 최소 지원 런타임 결과로 대체하지 않는다.
- [ ] 기존 클라이언트가 새 helloOk의 선택 필드를 무시하고 계속 동작하는지, 신형 클라이언트가 기능 없는 서버에 새 요청을 보내지 않는지 확인한다.
- [ ] winodbc의 실행 전 메타데이터·SQLCancel·질의 제한 시간 시험과 연결한다. ODBC의 HY008/HYT00 등과 서버 57014 사이의 진단 매핑을 문서화한다.
- [ ] TypeScript 6 컴파일, Node.js 22 이상, Bun 주요 시나리오와 10세션 동시성을 확인한다. 실행 컨텍스트를 비동기로 바꾸면서 트랜잭션/잠금/커밋 순서를 바꾸지 않았는지 점검한다.
- [ ] protocol.md·서버 매뉴얼·각 드라이버 PROGRESS.md·루트 PROGRESS.md를 함께 갱신한다. ODBC 완성을 위해 기존 통신 규약을 문서 없이 변경하지 않는다.

## 인수인계

- 이 작업은 네트워크 요청으로서의 준비·설명·취소이다. SQL 문법에 PREPARE/EXECUTE를 추가하는 별도 기능과 혼동하지 않는다.
- 실행 전 메타데이터를 얻기 위해 문장을 실행하는 편법, cancel을 항상 성공 처리하는 스텁, 세션 종료를 정상 요청 취소라고 알리는 구현은 완료 기준을 충족하지 않는다.
- 현재 저장 포맷을 바꿔야 하는 기능으로 계획하지 않는다. 필요한 변경이 발견되면 사양·영향 범위를 먼저 기록한다.
- 서버 구현과 일부 시험은 진행했으나 최종 검증은 완료하지 않았다. 사용자 종료 지시와 마지막 오류 수정 후의 미검증 범위는 [HANDOFF.md](HANDOFF.md)에 명시했다. 외부 드라이버의 새 API 연동도 후속 작업이다.
