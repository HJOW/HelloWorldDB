# 트랜잭션과 동시성 (7단계)

SQL 트랜잭션의 구조, 잠금, 커밋, 기다림의 처리를 한곳에 모은 문서이다.
사양은 AGENTS.md 상세 9, 10 이고, 저장 계층의 배치와 커밋 순서는 [storage-v1.md](storage-v1.md)에 있다.
코드의 머리 주석(`txn/transaction.ts`, `txn/lockManager.ts`, `session/session.ts`, `exec/dml.ts`)과 같은 내용을 줄거리 순서로 적었다.

## 1. 큰 그림

- 연결 하나가 세션 하나(`session/session.ts` 의 `Session`)이고, 세션 하나는 트랜잭션을 동시에 하나만 가진다.
- 격리 수준은 READ COMMITTED 하나이다. 조회는 커밋된 값과 자기 트랜잭션의 변경만 본다. 조회는 누구도 기다리지 않고 기다리게 하지도 않는다.
- 미커밋 변경은 **데이터 파일에 쓰지 않는다.** 트랜잭션이 메모리에 가진 오버레이에만 둔다. 커밋할 때 짧은 저장 배치로 한꺼번에 쓰고 fsync 한 뒤에 성공을 알린다.
- 자바스크립트는 한 스레드이고 문장은 처음부터 끝까지 동기로 실행한다. 한 문장 안에는 다른 세션의 문장이 끼어들지 않는다. 기다림은 문장과 문장 사이(문장을 다시 시도하기 직전)에서만 일어난다.
- 그래서 한 문장은 항상 일관된 커밋 상태를 읽고 쓴다.

## 2. 오버레이

`txn/transaction.ts` 의 `Transaction` 이 테이블마다 `TableOverlay` 를 가진다.

| 항목 | 내용 |
|---|---|
| `inserts` | 이 트랜잭션이 새로 넣은 행. `tempId` 로 구별하며 넣은 순서대로 둔다 |
| `updates` | 바꾼 커밋 행의 새 값. 키는 `pageId:slotId` |
| `deletes` | 지운 커밋 행의 키 |
| `signature` | 오버레이를 처음 만들 때의 테이블 정의 서명(힙 루트, 컬럼 이름과 타입). 커밋 때 같은지 본다 |

- 읽을 때(`readMergedRows`)는 저장된 커밋 행에 자기 오버레이를 덮어 합친다. 자기가 지운 행은 빠지고, 바꾼 행은 새 값으로, 새로 넣은 행은 뒤에 붙는다.
- 오버레이 행은 저장 행과 같은 값 배열이다. 따라서 트랜잭션 하나의 크기는 메모리에 제한된다(사양 10 이 인정한 제한).
- 자기 트랜잭션이 건드린 테이블은 인덱스를 타지 않고 합친 행을 전체 스캔한다. 커밋 때 인덱스까지 함께 쓰므로 커밋 뒤에는 인덱스 조회도 새 값을 본다.
- 되돌리기 기록(`UndoOp`)은 문장 표시와 세이브포인트가 같은 목록을 쓴다.
  - 문장이 실패하면 그 문장 표시(`mark`)까지 되돌린다(`truncateTo`). 트랜잭션은 유지한다.
  - `ROLLBACK TO` 는 세이브포인트 위치까지 되돌리고 그 세이브포인트는 남기며 그 뒤의 세이브포인트만 지운다.
  - 트랜잭션 전체 롤백은 오버레이를 버리고 잠금을 푸는 것으로 끝난다. 데이터 파일에는 쓴 것이 없기 때문이다.
- 자동 커밋 문장도 문장 하나짜리 트랜잭션 안에서 실행하고 문장 직후 커밋한다. 데이터 문장은 모두 같은 경로를 쓰므로 `QueryContext.txn` 은 항상 있다.

## 3. 잠금

`txn/lockManager.ts` 의 `LockManager` 가 데이터베이스에 하나 있고 모든 세션이 함께 쓴다.

### 3-1. 잠금 키

| 첫 글자 | 이름 | 걸리는 때 |
|---|---|---|
| `R` | 행 잠금 | 저장된 커밋 행을 바꾸거나 지울 때, `SELECT ... FOR UPDATE` 가 돌려주는 행 |
| `K` | PK 잠금 | 새 행을 넣거나 PK 값을 바꿀 때. 같은 PK 를 동시에 넣으려는 쪽끼리 순서가 정해진다 |
| `O` | 객체 잠금 | DDL 이 테이블 하나에 건다. 같은 테이블의 행·PK 잠금과 서로 충돌한다 |

- 키는 구분자 U+001F(식별자에 들어갈 수 없는 제어 문자)로 이어 붙인다. 잠금은 모두 배타이고 같은 소유자가 다시 걸면 허용한다.
- 소유자는 트랜잭션 번호이다. DDL 문장도 `Database.nextTransactionId()` 로 자기 번호를 받는다.
- 잠금은 커밋이나 롤백 때까지 쥔다. 일반 SELECT 는 잠그지 않는다. 자동 커밋에서 `FOR UPDATE` 는 문장이 끝나면 풀린다.
- `ROLLBACK TO SAVEPOINT` 는 변경은 되돌리지만 그 뒤에 얻은 행 잠금은 트랜잭션이 끝날 때까지 쥔다(알려진 한계).

### 3-2. 잠금 걸기의 단위

- DML 은 문장 끝에서 바뀐 행 전부의 키를 모아 **한꺼번에** 건다(`exec/dml.ts` 의 `applyToTransaction`, `tryAcquireAll`). 전부 걸리거나 하나도 안 걸린다.
- 하나라도 충돌하면 오버레이를 바꾸지 않고 충돌 오류를 던진다. 부분적으로 걸린 잠금이 남지 않는다.

## 4. 기다림과 교착

문장은 기다리지 않고 충돌하면 오류를 던진다. 기다리는 일은 세션이 한다.

| 실행 방식 | 잠금 충돌을 만나면 |
|---|---|
| `Session.execute` (동기) | 바로 `55P03`(`LockConflictError`)으로 실패한다. 그 문장의 변경은 되돌려진다 |
| `Session.executeAsync` (비동기) | 충돌한 키가 풀리기를 `transaction.lockTimeoutMs` 까지 기다린 뒤 **문장을 처음부터 다시 실행한다.** 그래서 기다린 쪽은 커밋된 새 값을 읽는다 |

- 통신 계층(9단계)과 동시성 테스트는 비동기를 쓴다. 단위 테스트와 단순 실행은 동기를 쓴다. 두 방식은 같은 문장 실행 코드를 쓴다.
- 대기 초과는 `55P03` 이고 그 문장만 실패한다. 트랜잭션은 유지된다.
- 교착 감지: 대기열에 들 때 대기 그래프(잠금 보유자와 같은 대기열에서 앞선 대기자)를 따라 고리를 찾는다. 고리를 닫은 쪽(방금 기다리려던 쪽)이 희생자이며, 그 트랜잭션을 통째로 롤백하고 `40P01` 을 알린다.
- 같은 세션의 비동기 문장은 호출한 순서대로 하나씩 처리한다(줄 세우기). 문장이 잠금을 기다리는 동안 같은 세션의 다음 문장도 기다린다. 그래서 기다리는 중의 확인용 조회는 다른 세션으로 해야 한다.
- 동기 `execute` 와 비동기 `executeAsync` 를 같은 세션에서 섞어 쓰면 안 된다. 비동기 문장이 기다리는 동안의 동기 호출은 막지 않는다.
- 세션을 닫으면(`Session.close`) 커밋하지 않은 변경은 롤백하고 잠금을 풀고 기다림을 취소한다(`08003`).

## 5. 커밋

`exec/dml.ts` 의 `commitTransaction` 이 맡는다. 순서는 다음과 같다.

1. 오버레이를 쓸 수 있는 이미지로 바꾼다(`overlayToImage`). 테이블이 없어졌거나 정의 서명이 달라졌으면 `40001` 로 실패하고 트랜잭션은 롤백된다.
   (PK 가 없는 테이블의 삽입은 잠금이 없어 DDL 과 부딪치지 않으므로 이 검사가 막는다)
2. 여러 문장 트랜잭션(명시적 트랜잭션, 자동 커밋 OFF)이면 FK 로 엮인 테이블의 FK 를 "커밋 값 + 자기 변경" 기준으로 다시 확인한다(`revalidateReferences`). 어기면 `23503` 이고 롤백된다.
   문장 하나짜리 트랜잭션은 문장과 커밋 사이에 끼어들 틈이 없어 생략한다.
3. 테이블스페이스마다 저장 배치 하나를 열어 힙과 인덱스를 함께 쓴다(`writeImage`). 인덱스는 지운 행과 바꾸기 전 값의 항목을 **먼저 모두 지운 뒤** 새 항목을 넣는다.
   같은 PK 를 지우고 다시 넣거나 PK 값을 맞바꾸어도 유일 인덱스에서 부딪치지 않는다.
4. 배치를 커밋한다. 저장 계층의 순서는 데이터 페이지 → 파일 헤더 → fsync → 캐시 공개이다. fsync 를 마친 뒤에 성공을 응답한다.
5. 성공하든 실패하든 트랜잭션은 끝나고 잠금은 풀린다.

쓰는 순간에는 다른 문장이 끼어들 수 없으므로(한 스레드, 동기 실행) 저장 배치의 충돌(`40001`)이 생기지 않는다.

테이블스페이스를 둘 이상 건드린 트랜잭션의 커밋은 테이블스페이스마다 배치 하나씩이며 서로 원자적이지 않다. WAL 이 없으므로 커밋 도중 중단되면 일부만 반영될 수 있고(사양 12), 정상 종료 표시와 체크섬으로 감지만 한다.

## 6. DDL 과 자동 커밋

- DDL(테이블스페이스·테이블·뷰·인덱스·TRUNCATE)은 실행 전에 진행 중인 트랜잭션을 커밋한다. 커밋이 실패하면 DDL 은 실행하지 않는다. 실패한 DDL 도 앞선 커밋은 되돌리지 않는다.
- DDL 은 대상 테이블과 FK 로 엮인 테이블에 객체 잠금(`O`)을 걸어 실행하고 푼다. 새로 만드는 객체는 잠그지 않는다. `DROP TABLESPACE` 는 그 안의 모든 테이블에 건다.
- 다른 트랜잭션이 그 테이블의 행을 잠그고 있으면 동기 실행은 `55P03`, 비동기 실행은 기다린다.
- 사용자·권한·테이블스페이스 관리 문장(GRANT, REVOKE, CREATE USER 등)도 같은 규칙(실행 전후 자동 커밋, 롤백 불가)을 따른다(8단계).

## 7. 트랜잭션 문장의 규칙

- `BEGIN` / `START TRANSACTION`: 이미 트랜잭션이 있으면 `25001`.
- `SAVEPOINT`, `ROLLBACK TO`, `RELEASE SAVEPOINT`: 트랜잭션이 없으면 `25P01`. 단, 자동 커밋이 OFF 이면 `SAVEPOINT` 가 트랜잭션을 시작한다. 없는 세이브포인트는 `3B001`.
- `COMMIT`, `ROLLBACK`: 트랜잭션이 없어도 오류가 아니다.
- `SET AUTOCOMMIT ON`: 진행 중인 트랜잭션을 커밋한다(MySQL 과 같음). OFF 이면 첫 문장에서 트랜잭션이 자동으로 시작된다. SELECT 도 시작시킨다.
- `SET TRANSACTION ISOLATION LEVEL` 은 READ COMMITTED 만 받는다.

## 8. 오류 번호

| 번호 | SQLSTATE | 뜻 |
|---|---|---|
| 6000 | `55P03` | 잠금 대기 초과, 충돌 |
| 6001 | `40P01` | 교착 |
| 6002 | `3B001` | 세이브포인트 없음 |
| 6003 | `08003` (`57P01` 도 이 번호) | 세션 닫힘 |
| 6004 | `25001` | 이미 트랜잭션 중 |
| 6005 | `25P01` | 트랜잭션 없음 |
| 6006 | `40001` | 커밋 때 전제가 깨짐(테이블 정의 변경 등) |

## 9. 알려진 한계

사양을 어기는 것은 없고, 단순함을 위해 보수적으로 동작하는 부분이다.

- 삭제 중인 행의 PK 를 다른 트랜잭션이 다시 넣으려 하면 기다리지 않고 바로 `23505` 가 난다(삭제가 커밋되기 전에는 커밋된 행이 아직 보이므로).
- 잠금은 전부 배타이다. FK 의 부모 행을 읽는 것만으로는 잠그지 않고, 대신 커밋 직전에 FK 를 다시 확인한다.
  그래서 부모를 지우는 트랜잭션과 자식을 넣는 트랜잭션이 겹치면 한쪽이 커밋에서 `23503` 으로 실패한다. 기다리게 하는 방식이 아니다.
- 한 문장이 읽고 쓰는 테이블 전체를 메모리 이미지로 읽는다(6단계부터의 방식). 큰 테이블에서는 느리다. 행 단위 접근은 하지 않았다.
- `ROLLBACK TO SAVEPOINT` 뒤에도 그 사이에 얻은 행 잠금은 트랜잭션이 끝날 때까지 쥔다.
- 행 쓰기 도중 `heap.update` 가 RowId 를 바꾸지 않는다는 6단계의 가정을 쓴다. 바뀌는 구현이 되면 오버레이의 `pageId:slotId` 키 방식을 다시 봐야 한다.
